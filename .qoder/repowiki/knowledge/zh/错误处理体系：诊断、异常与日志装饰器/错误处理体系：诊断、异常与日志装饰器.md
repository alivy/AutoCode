该仓库是一个基于 Roslyn IIncrementalGenerator 的 C# 代码生成框架，其错误处理体系由三个层面构成：编译期诊断（Analyzer/Source Generator）、运行时异常传播、以及通过源码生成注入的日志装饰器。

## 1. 编译期诊断（Diagnostic）
- AutoCode.Analyzers 使用 Microsoft.CodeAnalysis.DiagnosticDescriptor 定义一组静态诊断规则，按分类组织在 `AutoCodeDiagnosticDescriptors.cs` 中，包括 AC001~AC006 等编号，覆盖接口一致性检查、分层违规、命名规范等场景，严重级别为 Warning 或 Info。
- AutoCode.Map 模块同样通过 `DiagnosticDescriptors.cs` 定义 RMG002/RMG008/RMG046 等映射相关诊断，严重级别统一为 Error，用于阻止不合法的映射配置。
- 所有诊断均通过 `DiagnosticCategories` 常量集中管理分类（如 Usage、Design、Mapper），便于 IDE 和编译器聚合展示。

## 2. 运行时异常与传播
- 业务层示例（APP.WebAPI.Services.UserService）在参数校验失败时直接抛出 `ArgumentException`，并通过字符串拼接错误信息；未使用自定义异常类型或统一的错误响应模型。
- CLI 工具（AutoCode.Cli/Program.cs）采用返回值 + Console 输出方式报告模板验证错误，未使用异常流控制逻辑。
- 生成的日志装饰器（LogDecoratorGenerator）对每个方法包裹 try/catch，捕获 `Exception` 后调用 `_logger.LogError` 记录堆栈与耗时，随后 `throw;` 原样重新抛出，确保异常不会吞没。

## 3. 日志装饰器模式（Decorator）
- LogDecoratorGenerator 扫描标记了 `[AutoLog]` 的类，自动生成同名 Logging 前缀的装饰器类，实现目标接口并委托内部实例。
- 对同步/异步/void/返回值四种方法签名分别生成 try/catch 包装，统一记录开始、完成、异常三种状态，异常路径始终 rethrow。
- 该模式将横切关注点（日志+异常捕获）从业务代码中剥离，但并未改变异常语义——异常仍向上传播至调用方。

## 4. 约定与约束
- 诊断规则通过 DiagnosticDescriptor 静态字段暴露，ID 采用字母前缀+数字（ACxxx、RMGxxx），严重级别区分 Error/Warning/Info。
- 日志装饰器强制要求被装饰类实现一个非 DI 基接口的业务接口，且仅对普通方法生效。
- 业务层未建立统一的错误码或 Result 模式，异常类型选择随意（如 ArgumentException），缺乏跨模块的一致性。
- 未使用 panic/recover（C# 无此概念），也未见全局异常处理中间件（如 ASP.NET Core 的 ExceptionHandlerMiddleware）的配置。
